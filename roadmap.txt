PHASE 2 — ML INTEGRATION: SLIDING WINDOW FEATURE EXTRACTOR IN server.py
--------------------------------------------------------------------------------

The core challenge: the ML model works on WINDOWS of 25 packets, not individual
packets. server.py must:
  (a) Buffer incoming packets from the engine stream
  (b) Compute the 11 features once a window of 25 is filled
  (c) Run both ML models on the feature vector
  (d) Attach the result back to each packet in the window (or emit a window event)

[x] 2.1  Created server/ml_bridge.py — the window feature computer ✅
         - Class: PacketWindowBuffer(window_size=25)
         - Method: add_packet(packet_dict) → returns feature_dict or None
         - Features to compute from engine NDJSON fields:
             packet_count          → len(window)
             avg_packet_size       → mean of packet sizes
                                     *** PROBLEM: engine does NOT emit packet_size ***
                                     → Need to add "size" field to engine JSON output
                                     → OR estimate: dport 443 ≈ 800 bytes avg, dport 53 ≈ 60 bytes
                                     → Recommended: add size to engine JSON (see Phase 3)
             tcp_count             → count where proto == "TCP"
             udp_count             → count where proto == "UDP"
             unique_ips            → len(set of src + dst IPs)
             syn_count             → *** PROBLEM: engine doesn't emit TCP flags in JSON ***
                                     → Add "flags" field to engine JSON OR default syn_count=0
             tcp_ratio             → tcp_count / packet_count
             syn_ratio             → syn_count / packet_count
             packet_size_std       → std of packet sizes (needs size field)
             avg_interarrival_time → mean diff of "ts" timestamps within window
             unique_ports          → len(set of dport values in window)

[x] 2.2  Created server/ml_predictor.py — loads and runs the models ✅
         - Load ml/threat_classifier.pkl  (Random Forest)
         - Load ml/anomaly_detector.pkl   (Isolation Forest)
         - Method: predict(feature_dict) → {
             "label":          "Normal" | "Attack",
             "confidence":     0.0 - 1.0,
             "anomaly_score":  float,
             "is_anomaly":     bool
           }
         - Use FINAL_FEATURES order from upgrade_and_retrain.py:
           ["packet_count","avg_packet_size","tcp_count","udp_count",
            "unique_ips","syn_count","tcp_ratio","syn_ratio",
            "packet_size_std","avg_interarrival_time","unique_ports"]
         - Confidence threshold: 0.80 (from ML model README)

[x] 2.3  Integrated ml_bridge + ml_predictor into server.py ✅
         - For each packet received from engine stdout:
             1. Parse JSON
             2. Feed into PacketWindowBuffer
             3. If window full (25 packets):
                 a. Compute features
                 b. Run ML prediction
                 c. Tag all 25 packets with {"threat": {...}} or emit a separate window event
             4. Stream enriched packet JSON as SSE

KNOWN ISSUES & DECISIONS TO MAKE
--------------------------------------------------------------------------------

ISSUE A: Packet size missing from engine JSON
  → The 11-feature ML model needs avg_packet_size and packet_size_std
  → Without "size" in JSON, we cannot compute these accurately
  → Options:
      (1) Add "size" field to engine C++ JSON output  ← RECOMMENDED
      (2) Estimate size from port/protocol heuristics ← quick hack
      (3) Retrain ML model dropping those 2 features  ← loses accuracy

ISSUE B: SYN count missing from engine JSON
  → syn_count is important for detecting SYN flood attacks
  → Options:
      (1) Add "flags" field to engine C++ JSON output ← RECOMMENDED
      (2) Default syn_count=0 (misses SYN floods)

ISSUE C: ENGINE_CMD uses relative paths
  → "..\engine\dpi_simple.exe" will fail if uvicorn is run from a different dir
  → Fix: use os.path.dirname(__file__) to build absolute paths

ISSUE D: Blocking architecture
  → Currently the engine decides what to block (rule_manager)
  → In 2.0, ML might want to block IPs/connections flagged as attacks
  → Options:
      (1) FastAPI sends block commands back to engine via stdin ← complex
      (2) Engine just reports; server maintains its own block list ← simpler
      (3) Engine exposes a REST/socket control interface ← cleanest long-term

ISSUE E: Model files are in server/ml/ (already there!)
  → anomaly_detector.pkl (1.4 MB) and threat_classifier.pkl (6.8 MB) exist
  → These are the trained models from the ML repo — ready to use
  → Just need the inference code (ml_predictor.py) to load them

IS THIS ACHIEVABLE? YES. 100%.
================================================================================

Both systems are well-structured and the integration point is crystal clear:

  Engine   → already emits NDJSON per packet (stdout, --json flag)
  ML Model → already trained, .pkl files already in server/ml/
  Bridge   → server.py is a FastAPI app that can buffer + enrich + stream

The main gap is the WINDOW AGGREGATION LAYER in server.py. The engine speaks
"one packet at a time" but the ML model thinks in "25-packet windows." We need
~100 lines of Python to bridge this. Everything else is plumbing.

The only tricky parts are:
  - Missing "size" and "flags" in engine JSON (fixable in C++)
  - Keeping the SSE stream responsive while buffering 25 packets
    (use asyncio + async generator for non-blocking streaming)
