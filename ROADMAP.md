## 0. Product definition

Cypher 2.0 is a **network traffic analysis and threat visibility platform** for a home lab, small office, or self-owned network.

It should:

- Capture live traffic from one network interface, or replay/upload a PCAP.
- Parse Ethernet/IPv4/TCP/UDP and extract flow metadata.
- Identify applications from TLS SNI, HTTP Host, DNS, and port heuristics.
- Detect suspicious behavior with deterministic rules and ML.
- Map findings to MITRE ATT&CK techniques.
- Explain alerts with a RAG layer grounded in ATT&CK and threat-intelligence sources.
- Show evidence in a dashboard with severity, confidence, and timeline.
- Export a report suitable for a lab investigation or portfolio demo.

It is **not** an inline IPS, does not decrypt TLS, and does not claim malware detection.

### Real-time definition

There are three different claims:

| Claim | Meaning | Feasibility |
|---|---|---|
| Real-time replay | Stream a PCAP to the dashboard at 1x/5x/10x | Easy; already partly built |
| Near-real-time live analysis | Capture live traffic and show detections in under ~2 seconds | Achievable and worth doing |
| Inline real-time prevention | Drop/block traffic in the kernel data path | Too ambitious; high risk; not required |

The target is **near-real-time live analysis**, not inline prevention. Detection and visibility are enough for the resume story and for a real lab tool.

## 3. Target architecture

```text
┌─────────────────────────────┐
│ Windows / Linux host        │
│                             │
│  Npcap / libpcap            │
│        │                    │
│        ▼                    │
│  C++ capture + DPI engine   │
│  - parse + flows            │
│  - SNI / HTTP / DNS         │
│  - app labels               │
│  - JSON contract            │
│        │ NDJSON / socket    │
│        ▼                    │
│  FastAPI backend            │
│  - single capture session   │
│  - feature extraction       │
│  - rules + ML               │
│  - MITRE mapping            │
│  - RAG explanations         │
│  - SSE broadcast            │
│  - Postgres sessions/flows  │
│        │                    │
│        ▼                    │
│  Next.js dashboard          │
│  - live packet table        │
│  - charts + timeline        │
│  - alert detail             │
│  - export                   │
└─────────────────────────────┘

Public demo:
  Render/Fly/Railway + Postgres + Vercel dashboard + sample PCAP replay
  no live capture of public traffic
  docker compose up reproduces the stack locally

Live mode:
  local machine / self-hosted box with Npcap or libpcap
```

### Architectural rules

- One long-lived engine process per capture session, not one per SSE client.
- One feature extraction implementation shared by training and serving.
- One canonical flow key for both directions.
- One JSON contract for replay and live modes.
- One detection event schema for rules, ML, and combined alerts.
- Public deployment is read-only; capture controls require auth.

## 5. ML plan in detail

### Why the current 11-feature model is not enough

The current model uses 25-packet windows with 11 aggregate features. That is useful for a demo but not for precise threat classification:

- `packet_count` is always 25.
- The window is global across all flows, so one attack can be diluted by normal traffic.
- `syn_count` is zero when the C++ path omits `flags`.
- Packet size is estimated from ports when `size` is missing.
- There is no per-host or per-flow context.
- There is no training or evaluation code in the repo.

### Target feature set

Per bidirectional flow:

- Duration, packet count, byte count, packets/sec, bytes/sec.
- TCP flags and ratios: SYN, ACK, FIN, RST, SYN/ACK, half-open.
- Source/destination ports and port class.
- Protocol, app label, SNI/Host, DNS QNAME.
- Packet size mean/std/min/max.
- Inter-arrival mean/std/min/max.
- Bytes in/out ratio, packet in/out ratio.
- Connection state and failure count.
- TLS version, certificate metadata, JA3/JA4 if available.

Per host/time window:

- Unique destination IPs and ports.
- Fan-out rate.
- DNS query rate and unique domains.
- Connection rate and failure rate.
- Beaconing regularity score.
- Outbound/inbound byte ratio.
- Service diversity.
- Top destinations and apps.

### Labels and MITRE mapping

Use a practical label set, not one label per ATT&CK technique:

- Normal
- Scan / Discovery
- DoS / DDoS
- Brute Force
- Bot / C2
- Infiltration / Exfiltration
- Other / Unknown

Map each label to one or more ATT&CK techniques with a confidence and evidence field.

### Evaluation

- Time-based train/validation/test split, not random packet split.
- Avoid leakage across flows from the same capture.
- Report per-class precision/recall/F1, macro F1, FPR, PR-AUC, and confusion matrix.
- Report latency and throughput.
- Include a baseline: rules only, ML only, combined.
- Publish a model card: data sources, labels, features, metrics, limitations, ethical use.

### Claim rules for recall/F1 numbers

Do not put a number such as "0.95 recall, 0.91 F1" on the resume until all of these are documented:

- The exact dataset and version (for example, CIC-IDS2017 + a self-captured normal baseline).
- Which class the recall refers to (attack vs normal, or per-class macro recall).
- Whether F1 is binary, macro, or weighted.
- The train/validation/test split, including time-based separation and deduplication.
- Whether the self-captured data contributed labels or only a normal baseline.
- The false-positive rate and the confusion matrix.
- The feature set and model version used for the result.

Be careful with CIC-IDS2017: it is widely used but old, has quality/labeling issues, and random splits can leak near-duplicate flows. Use deduplication, a time-based split, and at least one external validation set or a self-captured holdout. A realistic result may be lower than 0.95/0.91; report what you measure, not a target.

A safer claim format:

> "Achieved **0.XX macro F1** and **0.XX attack-class recall** on a deduplicated, time-based CIC-IDS2017 split, with **0.XX FPR**, validated against a self-captured normal-traffic holdout."

Only fill in the numbers after running the evaluation.

### Important correction

MITRE ATT&CK is a knowledge base of adversary tactics and techniques, **not a packet dataset**. You do not "train on MITRE attacks" directly. You train on labeled network intrusion data and/or controlled lab traffic, then map detections to ATT&CK techniques. Use that phrasing on the resume and in interviews.

## 6. Metrics

Track these in the README and roadmap updates:

- Engine throughput: packets/sec and MB/sec.
- Capture drop rate.
- Classification coverage: percent of packets with a non-generic app label.
- Detection quality: precision, recall, F1, FPR per class.
- Alert volume: alerts per hour and duplicate rate.
- Latency: packet -> detection -> dashboard.
- Dashboard: packets streamed, rows rendered, filter latency.
- Stability: uptime and engine restarts.

### Measured CIC-IDS2017 results

Binary Random Forest, test split (362,378 rows):

| Operating point | Precision | Recall | F1 | FPR |
|---|---:|---:|---:|---:|
| Validation-selected 0.81 | 0.9992 | 0.8529 | 0.9202 | 0.0001 |
| Deployment 0.50 | 0.9903 | 0.8963 | 0.9410 | 0.0019 |
| High-recall 0.02 | 0.8168 | 0.9516 | 0.8791 | 0.0455 |

- Test ROC-AUC: 0.9922
- Test PR-AUC: 0.9797
- IsolationForest test ROC-AUC: 0.8416
- IsolationForest attack detection rate: 14.02%, normal FPR: 1.42%

The claim "0.95 recall and 0.91 F1" is not true at a single threshold. At 0.05 the model reaches 0.9289 recall and 0.9112 F1; at 0.02 it reaches 0.9516 recall but F1 drops to 0.8791. Use an operating point, not a disconnected pair of numbers.

Rule engine on the synthetic `test_attack.pcap`:

- 6 rule alerts: port_scan, syn_flood, dns_flood, suspicious_port, brute_force, beaconing.
- Severity split: 4 high, 2 medium.
- MITRE techniques: T1046, T1498 (2), T1571, T1110, T1071.
- The flow ML model returned Normal for all synthetic attack flows; the rules caught them.

## 8. Risks and non-goals

### Risks

- Dataset quality and licensing.
- MITRE mapping is approximate; one technique can map to several behaviors.
- False positives from anomaly detection.
- Live capture permissions and privacy.
- Cloud cannot capture arbitrary live traffic.
- Performance limits at high packet rates.
- Scope creep from adding too many app signatures.
- TLS 1.3 ECH and QUIC reduce SNI visibility.
- No TCP reassembly means split Client Hellos can be missed.

### Non-goals

- Inline IPS or automatic traffic blocking.
- TLS decryption.
- Malware detection or sandboxing.
- Carrier-grade line-rate processing.
- Full MITRE ATT&CK technique coverage.
- Capturing other people's traffic without consent.
- Storing payloads or personal data.

## 11. Decision log

| Decision | Choice | Reason |
|---|---|---|
| Real-time scope | Live analysis, not inline IPS | Safe, feasible, enough for resume |
| Public demo | Replay/upload only | Cloud cannot capture arbitrary traffic |
| Dashboard | Next.js (recommended) | Stronger resume signal; React/Vite is acceptable |
| Backend deploy | Render/Fly.io/Railway | Simple FastAPI hosting |
| Database | PostgreSQL | Real schema, indexes, migrations, and SQL evidence |
| Model distribution | Git LFS or release artifact | Avoid bloating the repo |
| ML target | Multi-class + anomaly + rules | More realistic than one model for everything |
| MITRE | Map detections to techniques | ATT&CK is not a packet dataset |
| RAG scope | ATT&CK knowledge base first, one optional feed | Grounded, cheap, and testable before adding live CTI |
| Metric claims | Only after measured, time-based evaluation | Prevents unsupported resume numbers |
| Capture library | Npcap on Windows, libpcap on Linux | Standard and well documented |
